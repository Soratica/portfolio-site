Host layer

Everything runs on one physical machine running Proxmox VE. Workloads live in LXC containers rather than full VMs: they share the host kernel, so they start in seconds and leave more of the machine's memory for the work itself.

Two containers carry what you see on the panel:

  • LXC 100, docker-ct. Docker plus build tooling. Every image on the panel is built here.
  • LXC 102, k3s-learn. A Debian 12 container running a single-node k3s cluster. It has no build tooling at all; it only runs images.

Both are unprivileged: root inside the container maps to an unprivileged UID range on the host, so a process that escapes a container lands on the host as an unprivileged user. That's the default I start from, and the reason file ownership on bind mounts needs a little care.

After one host reboot, both containers stayed down because neither was set to start on boot. I turned on onboot for both, and the deploy watcher now waits two minutes after boot before its first run so the containers are up when it reaches for them.

The cluster

k3s gives me a real Kubernetes API in a small footprint. The cluster runs:

  • Traefik as the ingress controller, routing by hostname to each app's Service.
  • local-path as the default StorageClass, binding volumes on the node when a pod first needs them.
  • kube-prometheus-stack (Prometheus, Grafana, Alertmanager) in a monitoring namespace.

Each app gets its own namespace, with credentials held in Kubernetes Secrets rather than in images or repos.

No registry, on purpose (for now)

There's no image registry. Images are built in docker-ct, saved to a tarball, streamed straight into the k3s container through pct exec on the host, and imported into containerd with k3s ctr images import. Deployments use imagePullPolicy: Never, so the cluster only ever runs what was imported.

The catch: kubectl rollout restart on its own changes nothing. A new image has to be built and imported first. The deploy line handles that, so I don't have to remember.

One stateful detail worth mentioning

Gym Hero needs multi-document transactions, which MongoDB only supports on a replica set. It runs as a single-member replica set with a keyfile from a Secret. After initialising it, I had to reconfigure the member's advertised host to the Service name, because pod hostnames don't resolve inside the cluster and the driver failed with ENOTFOUND until I did.

Getting traffic in

Nothing on the panel is reached through an open port. A Cloudflare Tunnel runs as a cloudflared Deployment in its own namespace. It dials out to Cloudflare's edge, and requests for this site and the apps come back down that connection to Traefik.

That's the route the panel lights up when it loads: your browser, the Cloudflare edge location that answered you, the tunnel, Traefik, then the portfolio pod that served the page. The edge code and pod name on the panel come from your actual request.

Each Ingress carries two host rules, the public hostname and a .local name, so the apps stay reachable on the LAN by name even if the tunnel is down.

One lesson: a public hostname added in the Cloudflare dashboard can fail to save while the tunnel still shows as connected, which leaves the name not resolving. I now check every new hostname against a public resolver before calling it done.

The deploy line

Pushing to GitHub is the whole deploy. A systemd timer on the Proxmox host runs a watcher script every five minutes. It lives on the host because that's the one place that can reach into both containers.

  1. Fetch. For each watched repo, git fetch inside docker-ct and compare HEAD with the remote branch.
  2. Fast-forward only. If it's behind, merge with --ff-only. Anything that isn't a clean fast-forward is logged and left alone rather than forced.
  3. Build the image in docker-ct.
  4. Ship it: docker save, stream it through the host into k3s-learn, ctr images import.
  5. Roll out: kubectl rollout restart, then rollout status with a timeout, so a bad rollout shows up in the journal instead of passing silently.
  6. Record the deploy in the register you can see on the panel.

The run is guarded by flock, so a slow build can't overlap with the next timer tick. Gym Hero, Music Shuffler and this portfolio are on the line. Job Planner is still deployed by hand.

The status feed

The lamps needed live data without opening a new way into the cluster. So nothing in your browser ever talks to the Kubernetes API.

  • A CronJob runs every minute under its own ServiceAccount. Its permissions are read-only and scoped: get and list on Deployments and StatefulSets in the namespaces shown on the panel, get on nodes, and permission to update exactly one ConfigMap.
  • It writes an allow-listed summary: per station, ready replicas, desired replicas, a derived state and the last rollout time. Anything not on the list never leaves the cluster.
  • The deploy watcher publishes the host readings and the register the same way, into a second ConfigMap.
  • Both ConfigMaps are mounted into this site's nginx pod as plain files under /status/. There's no new listener and no proxy, and the feed is served with no-store so readings are never cached.

If the feed stops updating, the panel says so: readings older than five minutes go dark rather than showing an old green.

Capacity

The host's memory is shared between every container on it, and each container has a fixed memory allocation rather than an unbounded share. The monitoring stack is currently scaled to zero replicas, and the panel shows it as switched out rather than hiding it. Switching it back in is a replica count, not a reinstall.

Trade-offs I'd revisit

Single node, single host
There's no high availability. A host reboot takes everything down until the containers start again. Fine for a lab; the next step would be a second node, plus storage that isn't tied to one disk.
No registry, :latest tags
Simple, but it couples the build container to the cluster and makes rollbacks manual. I'd add a small in-cluster registry and tag images with the commit SHA, so a rollback is a one-line change.
Polling instead of webhooks
Polling needs no inbound path for GitHub to call, which suits a tunnel-only setup. The price is up to five minutes between push and deploy.
Manifests applied by hand
Most manifests were applied ad hoc with kubectl apply. This portfolio's manifests now live in its repo. The other apps are next, and that's the step before trying a GitOps controller.
